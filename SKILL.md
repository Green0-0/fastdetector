FastDetector is a pipeline for end-to-end development of AI text detectors, with enough flexibility to also filter and generate synthetic data for any domain!

## Package Setup
You should use ``uv`` when setting up FastDetector. When installing vLLM or Aphrodite to run LLMs for the generation and filtering pipelines, it must be in a seperate venv, ideally named ``.vllm`` or ``.aphrodite``. FastDetector is also compatible with general OAI endpoints. It goes without saying that the appropriate versions of torch/cuda should be installed to work with vLLM.

Additionally, an appropriate flash attention wheel should be installed for the qwen embedding models, see: https://github.com/mjun0812/flash-attention-prebuild-wheels/. 

## Codebase
The codebase is split into four distinct paths: prompting, pipelining (used for filtering and generation), statistics, and analysis. There are also generic scripts, such as src/fastdetector/utils.py primarily for managing hf datasets, src/fastdetector/frontend/toml_config.py and src/fastdetector/frontend/toml_loader.py for managing TOML configurations. Two dataset-management entrypoints sit outside the four paths and are driven by arguments rather than a TOML: scripts/shard_dataset.py (splits the raw dataset into shards; run before anything else) and scripts/delete_datasets.py (housekeeping). Everything in the archives can be ignored; these scripts are depreciated and likely broken. Do NOT update the archive scripts, these will be deleted soon.

### Testing
The suite lives in tests/ and is documented in tests/README.md. It is one pytest suite with opt-in tiers expressed as markers: unmarked tests are fast, offline and CPU-only (``uv run pytest``), while ``gpu``, ``slow``, ``network`` and ``vllm`` are deselected by default and selected with ``-m`` (e.g. ``uv run pytest -m gpu``). Run the default tier after any change to src/ or scripts/; it covers the config models, prompt handling, sampling-param translation, the exact scorer (checked against a naive reference using tiny in-process models, no downloads), the metrics, and the committed config/ and prompts/ files. Do not add downloads or GPU requirements to unmarked tests - use the offline fixtures in tests/conftest.py instead.

### Prompting
Example prompts are written in sample_prompts; these can just be basic json lists. However, these must be formatted to be a list of json dicts with:
```
{
    "chat_turns": A list of chat turns sent to the AI, where {{DOC}} references the document and {{RESP_N}} references a previous chat turn.,
    "use_multiturn": A boolean that when true, uses standard multiturn, but otherwise treats the latest message as a brand new message, with {{RESP_N}} markers used to fetch previous outputs.,
    "examples": A list of few-shot examples, where each example is a list with the first element being the human message and the second being the AI response.
    "metadata": Data used to ID the type of prompt this is.
}
```
See prompts/ for examples.

### Pipelining
Assuming the prompts are already parsed correctly, the pipe.py / engine_config.py / llm_utils.py / generator.py files in src/fastdetector/ will handle them with a pipeline config and generate the resulting dataset. Usages include gen.py (which generates AI responses) and filter.py (which processes human responses into continuous text sequences with no boilerplate), with their respective toml configurations. These scripts also include post-processing filters.

Importantly, everything including pipelining and afterwards supports dataset splitting/multi machine batching. This works by splitting a dataset into subsets, and having a seperate machine process each subset. The subset a machine processes is indexed by the batch-id that the entrypoints accept; this batch-id MUST not be duplicated (if you are batching). Every entrypoint, filter.py included, reads the shard named by its batch-id and writes its outputs back under that same shard config, so the shards a run creates are the shards the next stage consumes. Passing batch-id 0 is the single-machine scenario; note that filter.py's quantiles (and therefore its quantile conditions) are computed within a shard.

The shards are created up front by shard_dataset.py, which splits the raw dataset round-robin (use --contiguous for blocks instead) into shard_<i> configs written back to the dataset filter.py reads. Its --num-samples argument is the ONLY place a run's size is set: no config file carries a sample count, and the pipeline stages process every row of the shard they are given. There is also a delete_datasets.py housekeeping script which deletes the datasets a set of pipeline stages writes (dry run unless --yes is passed).

Cluster job scripts for every stage live in slurm/, one sbatch per entrypoint, with the sharded stages submitted as array jobs whose SLURM_ARRAY_TASK_ID is the batch-id. The three statistics stages all rewrite the same shard, so they must not run concurrently on the same batch-id.

### Statistics
Once you have a dataset of human-AI pairs, you can calculate a lot of statistics on them. These range from basic lexical distance metrics, to embedding metrics, editlens model edit scores, and even llm based metrics such as entropy or perplexity. The detailed code is specified in src/fastdetector/statistics, with some editlens code specified in src/fastdetector/modeling. Note that most functions are standardized to return distances instead of similarities, which may involve inverting the return value. There are three primary entry points with similarly named configuration files: stats/distance_stats.py which calculate embedding and lexical distances, llm_stats.py which calculates llm stats and llm-based classifier stats (such as binoculars), and editlens_stats.py which runs an editlens model. llm_stats.py loads its checkpoints in-process with transformers (main venv, no vLLM server) and computes all metrics exactly from full-vocabulary distributions, which are reduced on the fly and never stored; when binoculars is enabled both checkpoints are loaded together so the cross-model term can be computed in memory. Batch-id sharding keeps its usual meaning for llm_stats.py (one dataset subset per machine/run); within a run, the checkpoint(s) are replicated onto every visible GPU (devices = "auto") and all replicas work that single shard in parallel, so multi-GPU machines do not need one process per GPU.

### Analysis
None of the statistics scripts will generate a readme or results by themselves, you MUST run the analysis script, which uses the backend scripts in src/fastdetector/visualization. This script generates a comprehensive readme of all desired stats (configured in config/analysis.toml) and automatically builds graphs/charts and pushes to huggingface. A JSON spec of the results is also pushed, so it can be downloaded later and seperately analyzed locally (see compare_summary.py).

The readme has a fixed section list, built in scripts/analysis.py `build_readme`: the run configuration (the same parameter dump gen.py and filter.py write) and a data-derived summary of what was measured, a table of contents, univariate stats and a correlation heatmap over every statistic of interest (the distance metrics plus each classifier's score column per base column), distance and classifier histograms over the whole dataset, a classifier comparison table (AUROC plus TPR/FPR at each classifier's pinned threshold) and the validation threshold sweeps behind it, one report per classifier broken down by prompt subset, and finally a hardcoded full report which currently reports the *first* configured classifier per generator model/genconfig. Rows a statistic is missing or non-finite for are counted in the univariate table's `Invalid/Error` column and excluded from that statistic's metrics rather than being allowed to NaN out a whole classifier. The contents list is generated from the headings that were actually emitted (`build_contents`), so every entry is a working link; do not hand-maintain a second list. Its heading must NOT be "Table of Contents": the Hugging Face card renderer strips a section with exactly that heading (list included), which is why the rendered card had no contents at all before it was renamed to "Contents".

The readme only ever covers what config/analysis.toml names. It is meant to list every statistic the pipeline can compute - all the distance metrics, EditLens score/bucket, and the llm_stats detectors (perplexity, entropy, top-p/top-k outliers, FastDetectGPT, Binoculars) as `[[classifiers]]` whose suffixes track `col_suffixes` in llm_stats.toml. Listing a statistic this particular dataset lacks is safe and intended: `select_available` evaluates what is present and the readme names the rest as skipped, which is how an unrun stats stage stays visible. Directions matter: perplexity, entropy, outlier rates and Binoculars are `lower_is_ai`, everything else is `higher_is_ai`.

Note: Statistics and analysis should work on datasets that were not generated by the pipeline as well, but may require minor modifications to config files to ensure the datasets with different formats are processed together.
